1. Qué es el proyecto

SneakHub es una tienda de tenis con dos roles: el cliente mira el catálogo, arma un carrito y compra; el administrador gestiona tenis, marcas, categorías y el estado de los pedidos.

Está hecho con tres piezas separadas que hablan entre sí:

App Flutter
Carpeta lib/. Lo que ve el usuario: pantallas, botones, carrito. Corre en Chrome, Android o escritorio.
⇄
API Spring Boot
Carpeta api/. Recibe peticiones HTTP, aplica las reglas del negocio y responde JSON. Puerto 8081.
⇄
Base de datos H2
Archivo api/data/sneakhub.mv.db. Guarda usuarios, tenis, pedidos… Solo la API la toca.

La app nunca toca la base de datos directamente. Siempre le pide las cosas a la API por HTTP, por ejemplo GET http://localhost:8081/api/v1/sneakers, y la API responde con JSON. Esta separación se llama arquitectura cliente-servidor, y la API es una API REST.

Lo que hace el cliente

  • Registrarse e iniciar sesión
  • Ver el catálogo con búsqueda y filtros (marca, categoría, género)
  • Ver el detalle de un tenis, elegir talla y cantidad
  • Carrito con validación de stock
  • Comprar (crear pedido) y ver sus pedidos

Lo que hace el admin

  • Panel con estadísticas (ventas, stock bajo, pendientes)
  • Crear, editar y borrar tenis
  • Crear marcas y categorías
  • Ver todos los pedidos y cambiar su estado
  • Cancelar un pedido devuelve el stock

2. Una compra de punta a punta

Antes de entrar al detalle, este es el recorrido completo cuando el cliente pulsa “Comprar”. Cada paso se explica más adelante.

  1. Flutter (pantalla): CartScreen llama a OrderService.create(items).
  2. Flutter (servicio): el servicio usa Dio para enviar POST /api/v1/orders con el JSON {"items":[{"sneakerId":1,"size":40,"quantity":2}]}.
  3. Flutter (interceptor): antes de salir, el interceptor le pega el encabezado Authorization: Bearer <token>.
  4. Spring Security: la petición pasa por la cadena de filtros, que valida la firma y la fecha del JWT. Si está mal, responde 401 y nunca llega al controller.
  5. Controller: OrderController.create() recibe el JSON ya convertido en un objeto Java (OrderRequest), lo valida con @Valid y llama al servicio.
  6. Service: OrderService.create() busca el usuario y los tenis, valida talla y stock, crea el pedido y descuenta el stock, todo dentro de una transacción.
  7. Repository: orders.save(order), y Hibernate genera los INSERT / UPDATE en H2.
  8. Respuesta: el servicio convierte la entidad en un DTO (OrderResponse), Spring lo convierte en JSON y responde 201 Created.
  9. Flutter: Order.fromJson() convierte el JSON en un objeto Dart, se vacía el carrito, se recargan los datos y se navega al detalle del pedido.

3. Qué es Spring y Spring Boot

Spring es un framework de Java para hacer aplicaciones de servidor. La diferencia entre una librería y un framework es clave:

Librería

Tú la llamas. Ejemplo: Math.max(a, b). Tu código manda.

Framework

Él te llama a ti. Tú escribes clases con ciertas anotaciones y Spring decide cuándo crearlas y cuándo ejecutar sus métodos. A eso se le llama Inversión de Control (IoC).

En Java “puro” tendrías que crear un servidor, leer el socket, parsear el HTTP, convertir JSON a objetos, abrir la conexión a la BD, escribir SQL… Spring ya trae todo eso hecho, y tú solo escribes la lógica de tu tienda.

¿Y Spring Boot?

Spring “a secas” exigía mucha configuración (archivos XML, configurar el servidor Tomcat aparte, etc.). Spring Boot es una capa encima que lo hace fácil:

  • Starters: en vez de elegir 15 librerías compatibles, agregas una sola, por ejemplo spring-boot-starter-data-jpa, y trae todo lo necesario.
  • Auto-configuración: Boot mira qué librerías hay y se configura solo. ¿Hay H2 en el classpath? Entonces crea la conexión a H2. ¿Hay Spring Security? Entonces protege los endpoints.
  • Servidor embebido: trae Tomcat adentro. No instalas un servidor; la API es un programa Java normal con main que escucha en el puerto 8081.
  • application.properties: un solo archivo para cambiar puerto, BD, etc.
Idea claveSpring Boot = Spring + configuración automática + servidor incluido. Por eso tu proyecto tiene tan poco código “de infraestructura”: casi todo lo que escribiste es lógica del negocio.

4. Beans e inyección de dependencias

Este es el concepto más importante de Spring y casi seguro te lo preguntan.

El problema en Java puro

// Sin Spring: cada clase crea lo que necesita
public class OrderService {
    private OrderRepository orders = new OrderRepository(new Connection("jdbc:..."));
    private SneakerService sneakers = new SneakerService(...); // ¿y sus dependencias?
}

Cada clase tiene que saber cómo construir a las demás. Todo queda acoplado, es difícil de probar y terminas con muchas instancias repetidas.

La solución de Spring

Spring tiene un contenedor (el ApplicationContext): una “caja” donde él mismo crea los objetos importantes de la app y los guarda. A cada objeto que vive en el contenedor se le llama bean. Por defecto hay una sola instancia de cada bean (singleton).

Tú solo declaras qué necesitas en el constructor, y Spring te lo pasa. Eso es la Inyección de Dependencias (DI):

api/.../service/OrderService.java 
@Service                      // "Spring, crea un bean de esta clase"
public class OrderService {
    private final OrderRepository orders;
    private final UserRepository users;
    private final SneakerService sneakerService;

    // Spring ve este constructor, busca esos 3 beans y los pasa solo.
    public OrderService(OrderRepository orders, UserRepository users, SneakerService sneakerService) {
        this.orders = orders;
        this.users = users;
        this.sneakerService = sneakerService;
    }
}

Nunca escribes new OrderService(...). Spring arma el “árbol” completo: crea los repositorios, luego SneakerService (que necesita repositorios), luego OrderService (que necesita SneakerService), luego OrderController (que necesita OrderService).

¿Y @Autowired?En tutoriales viejos verás @Autowired encima de un atributo. Hace lo mismo, pero la forma recomendada hoy es la del proyecto: inyección por constructor, sin anotación (si la clase tiene un solo constructor, Spring lo usa). Así los campos pueden ser final y es fácil hacer pruebas pasando objetos falsos.
“¿Qué es un bean?”: un objeto creado y administrado por el contenedor de Spring. “¿Qué es la inyección de dependencias?”: en vez de que una clase cree sus dependencias con new, el contenedor se las entrega (aquí por el constructor). Reduce el acoplamiento y facilita las pruebas.

5. ¿Es MVC? Las capas del proyecto

Sí, más o menos, pero con un matiz importante. El módulo que usa la API se llama literalmente Spring MVC (spring-boot-starter-webmvc). Vamos por partes.

MVC clásico

Model
Los datos y las reglas.
View
Lo que se muestra (HTML).
Controller
Recibe la acción del usuario, usa el modelo y elige la vista.

En una app web MVC “tradicional” (con Thymeleaf o JSP), el servidor genera el HTML. Aquí no: tu API no genera pantallas, devuelve JSON. La “vista” real es la app Flutter.

Cómo se mapea en SneakHub

MVCEn la APIPaquete
ControllerRecibe HTTP, valida la entrada y delega. No tiene reglas de negocio.controller/
ModelSe divide en tres capas: service (reglas), repository (acceso a datos) y entity (las tablas como clases).service/, repository/, entity/
ViewEl JSON que se responde (los DTOs) y, del otro lado, las pantallas de Flutter.dto/ + app Flutter

La arquitectura en capas (lo que de verdad se usa)

Más preciso que “MVC” es decir que la API usa una arquitectura en capas. Cada capa solo habla con la de abajo:

Controller
“¿Qué me pidieron?” HTTP ⇄ objetos Java
→
Service
“¿Está permitido? ¿Hay stock?” Reglas de negocio y transacciones
→
Repository
“Tráeme / guarda esto.” Consultas a la BD
→
Base de datos
Tablas en H2

Y transversalmente:

  • entity/: las clases que representan tablas. Las usan el repository y el service.
  • dto/: los objetos que entran y salen por HTTP. Los usan el controller y el service.
  • exception/: errores de negocio y su traducción a JSON.
  • config/: seguridad, JWT y datos iniciales.
¿Por qué separar así?Si mañana cambias H2 por MySQL, solo cambia la configuración, no los services. Si mañana haces una app de escritorio, los services y repositories quedan iguales. Cada clase tiene una sola responsabilidad, así que es fácil saber dónde buscar un bug: “el stock se descuenta mal” está en el service; “la URL no existe” está en el controller.
Respuesta corta: “Usa Spring MVC con arquitectura en capas. El controller es la C de MVC; el Model está repartido en services, repositories y entidades; y como es una API REST, la vista es JSON y la interfaz real la pinta Flutter.”

6. Qué pasa al arrancar la API

api/.../SneakHubApiApplication.java 
@SpringBootApplication
public class SneakHubApiApplication {
    public static void main(String[] args) {
        SpringApplication.run(SneakHubApiApplication.class, args);
    }
}

@SpringBootApplication es la suma de tres anotaciones:

  • @Configuration: esta clase puede definir beans.
  • @EnableAutoConfiguration: activa la auto-configuración de Boot.
  • @ComponentScan: busca beans en este paquete y sus subpaquetes. Por eso todas las clases están bajo com.sneakhub.api.

Lo que ocurre cuando ejecutas .\mvnw spring-boot:run

  1. Maven compila el código y arranca el main.
  2. Spring lee application.properties.
  3. Hace el component scan y registra todas las clases anotadas.
  4. La auto-configuración crea la conexión a H2 (el DataSource). Si el archivo de la BD no existe, H2 lo crea.
  5. Hibernate lee las clases @Entity y, como ddl-auto=update, crea o actualiza las tablas.
  6. Spring Data crea las implementaciones de los repositorios.
  7. Se crean los services, controllers, la configuración de seguridad, etc., inyectando dependencias.
  8. Arranca Tomcat en el puerto 8081.
  9. Se ejecuta DataSeeder.run(): si no hay usuarios, inserta los datos de ejemplo.
  10. En consola sale Started SneakHubApiApplication. La API ya recibe peticiones.

9. La base de datos: ¿existe? ¿quién la creó?

Sí, el proyecto usa una base de datos real, relacional y con SQL: H2. No la creaste tú porque entre H2, Spring Boot y Hibernate la crearon solos. Así funciona:

Paso 1: H2 es una base de datos “embebida”

MySQL o PostgreSQL son programas aparte: los instalas, los arrancas y creas la BD con CREATE DATABASE. H2 es distinto: es una librería Java (está en el pom.xml) que corre dentro del mismo proceso de la API. No hay nada que instalar.

Paso 2: la URL dice “usa este archivo”

jdbc:h2:file:./data/sneakhub

Significa: “base H2 en modo archivo, en ./data/sneakhub”. La ruta es relativa a la carpeta desde donde ejecutas la API (api/). Si el archivo no existe, H2 lo crea vacío. Por eso apareció api/data/sneakhub.mv.db la primera vez que arrancaste. (sneakhub.trace.db es solo un registro de errores de H2.)

Spring Boot lee esa URL y, por auto-configuración, crea el DataSource (el objeto que da conexiones a la BD) sin que escribas código.

Paso 3: Hibernate crea las tablas a partir de tus clases

Con spring.jpa.hibernate.ddl-auto=update, Hibernate mira cada clase @Entity al arrancar y genera el SQL de las tablas que falten. Por ejemplo, de Brand sale algo así:

create table brands (
    id   bigint generated by default as identity,
    logo varchar(255),
    name varchar(255) not null unique,
    primary key (id)
);
Valor de ddl-autoQué hace al arrancar
noneNada: tú creas las tablas.
validateRevisa que las tablas coincidan con las entidades; si no, falla.
updateCrea las tablas o columnas que falten. No borra datos. (el del proyecto)
createBorra todo y crea de cero en cada arranque.
create-dropComo create, y además borra al apagar (útil en pruebas).

10. Entidades (JPA / Hibernate)

ORM (Object-Relational Mapping) significa trabajar con objetos Java y que una librería los traduzca a filas de tablas. JPA es la especificación (las reglas y anotaciones, en el paquete jakarta.persistence) y Hibernate es la implementación que hace el trabajo de verdad.

api/.../entity/Sneaker.java (resumido) 
@Entity                               // esta clase es una tabla
@Table(name = "sneakers")              // con este nombre
public class Sneaker {
    @Id                                // llave primaria
    @GeneratedValue(strategy = GenerationType.IDENTITY) // autoincremental
    private Long id;

    @Column(nullable = false)          // NOT NULL
    private String name;

    @Enumerated(EnumType.STRING)       // guarda "UNISEX" y no 2
    private Gender gender;

    @ElementCollection                 // lista de valores simples → tabla aparte
    @CollectionTable(name = "sneaker_sizes", joinColumns = @JoinColumn(name = "sneaker_id"))
    private List<Integer> sizes;

    @ManyToOne(optional = false)       // muchos tenis → una marca
    @JoinColumn(name = "brand_id")      // columna de llave foránea
    private Brand brand;
}

Relaciones del proyecto

AnotaciónDóndeSignificado
@ManyToOneSneaker.brand, Sneaker.category, Order.user, OrderItem.order, OrderItem.sneakerMuchos de esta clase apuntan a uno de la otra. Crea la columna xxx_id.
@OneToMany(mappedBy="order", cascade=ALL, orphanRemoval=true)Order.itemsUn pedido tiene muchos ítems. mappedBy: la FK está en OrderItem.order. cascade=ALL: al guardar el pedido se guardan sus ítems. orphanRemoval: si quitas un ítem de la lista, se borra.
@ElementCollectionSneaker.sizes, Sneaker.imagesListas de números o textos que no son entidades propias.

Detalles que demuestran que entiendes

  • Constructor protected vacío (en User, Brand, Order…): JPA lo necesita para crear el objeto al leer de la BD; es protected para que tu código no lo use por error.
  • OrderItem.unitPrice guarda el precio al momento de comprar. Si el admin sube el precio mañana, los pedidos viejos no cambian.
  • Order.addItem() mantiene las dos direcciones de la relación (item.setOrder(this)) y suma el total. Así nadie se olvida de calcularlo.
  • Enums (Role, Gender, OrderStatus) se guardan como texto con EnumType.STRING. Si se guardaran como número y alguien reordenara el enum, los datos quedarían mal.
  • La contraseña se guarda cifrada con BCrypt, nunca en texto plano.

Un repositorio es la clase que habla con la BD. En Spring Data solo escribes una interfaz y Spring genera la implementación al arrancar.

Consulta escrita a mano (JPQL)

Para los filtros del catálogo se usa @Query con JPQL, que se parece a SQL pero usa nombres de clases y atributos, no de tablas:

api/.../repository/SneakerRepository.java 
@Query("""
    select s from Sneaker s
    where (:brandId is null or s.brand.id = :brandId)
      and (:categoryId is null or s.category.id = :categoryId)
      and (:gender is null or s.gender = :gender)
      and (:q is null or lower(s.name) like lower(concat('%', :q, '%')))
    order by s.id
    """)
List<Sneaker> search(@Param("brandId") Long brandId, ...);

El truco (:x is null or …) hace que cada filtro sea opcional: si Flutter no manda la marca, llega null y esa condición siempre es verdadera.

12. DTOs y validación

Un DTO (Data Transfer Object) es un objeto que solo sirve para transportar datos por HTTP. En el proyecto son record de Java (clases inmutables con constructor, getters, equals y toString automáticos).

¿Por qué no devolver la entidad directamente?

  • Seguridad: User tiene la contraseña. UserResponse no la tiene.
  • Ciclos: Order → items → order → items… al pasarlo a JSON sería infinito.
  • Contrato estable: puedes cambiar la tabla sin romper la app.
  • Forma cómoda: OrderItemResponse trae sneakerName, image y subtotal ya calculados para la app.

Request (lo que entra) vs Response (lo que sale)

@Transactional

Una transacción es un grupo de operaciones que se hacen todas o ninguna. Mira OrderService.create:

@Transactional
public OrderResponse create(String email, OrderRequest request) {
    User user = users.findByEmail(email).orElseThrow(...);
    Order order = new Order(user);

    // 1. Suma cantidades por tenis (2 tallas del mismo tenis cuentan juntas)
    Map<Long, Integer> requested = new HashMap<>();
    for (OrderItemRequest item : request.items())
        requested.merge(item.sneakerId(), item.quantity(), Integer::sum);

    // 2. Valida talla y stock de cada ítem
    for (OrderItemRequest item : request.items()) {
        Sneaker sneaker = sneakerService.get(item.sneakerId());
        if (!sneaker.getSizes().contains(item.size())) throw ApiException.badRequest(...);
        if (requested.get(sneaker.getId()) > sneaker.getStock()) throw ApiException.badRequest(...);
        order.addItem(new OrderItem(sneaker, item.size(), item.quantity()));
    }
    // 3. Descuenta stock (¡sin llamar a save del tenis!)
    order.getItems().forEach(i -> i.getSneaker().setStock(i.getSneaker().getStock() - i.getQuantity()));
    return OrderResponse.from(orders.save(order));
}

Si el tercer ítem no tiene stock, se lanza una excepción, la transacción hace rollback y nada de lo anterior queda guardado. Sin @Transactional podría quedar un pedido a medias.

Dirty checking: ¿por qué no hay save() al descontar el stock?

Dentro de una transacción, las entidades que leíste están administradas por Hibernate. Cuando cambias un atributo (setStock), Hibernate lo nota y, al terminar la transacción, hace el UPDATE solo. Por eso SneakerService.update() y OrderService.updateStatus() tampoco llaman a save.

@Transactional(readOnly = true) se usa en las consultas: avisa que no habrá cambios y Hibernate se ahorra trabajo.

Pregunta trampa: dos clientes compran el último par al mismo tiempoLas dos transacciones podrían leer stock = 1 a la vez. El proyecto no lo bloquea explícitamente. La solución estándar es agregar @Version a Sneaker (bloqueo optimista): la segunda transacción falla en vez de dejar el stock negativo. Mencionarlo muestra que entiendes las transacciones.

¿Qué es un JWT?

Un JSON Web Token es un texto de tres partes separadas por puntos: header.payload.firma. El payload de SneakHub se ve así (en Base64 en el token):

{ "iss": "sneakhub-api", "sub": "cliente@sneakhub.com",
  "role": "CUSTOMER", "type": "access",
  "iat": 1762424130, "exp": 1762427730 }
  • La firma se calcula con HMAC-SHA256 y la clave secreta app.jwt.secret. Si alguien cambia CUSTOMER por ADMIN, la firma ya no coincide y la API lo rechaza.
  • El payload no está cifrado, solo codificado: cualquiera puede leerlo (Flutter lo lee para saber el rol). Por eso no se ponen contraseñas ahí.
  • Es stateless: el servidor no guarda sesiones. Toda la información viaja en el token y basta con verificar la firma.

Access token y refresh token

Access (60 min)

Se manda en cada petición. Dura poco: si lo roban, sirve por poco tiempo. Lleva "type":"access".

Refresh (7 días)

Solo sirve para pedir tokens nuevos en /auth/refresh. Lleva "type":"refresh". El JwtConfig tiene un validador que impide usar un refresh como access y al revés.

Las clases que lo hacen

  • JwtConfig: crea los beans SecretKey, JwtEncoder (firma) y JwtDecoder (valida firma, fecha y que type == "access").
  • TokenService: arma los claims (sub = correo, role, type, exp) y genera los dos tokens.
  • jwtAuthenticationConverter() en SecurityConfig: lee el claim role y lo convierte en la autoridad ROLE_ADMIN o ROLE_CUSTOMER. hasRole("ADMIN") busca justamente ROLE_ADMIN.
  • PasswordEncoder (BCrypt): encode() al registrar, matches() al hacer login. BCrypt es un hash lento y con “sal”: el mismo texto da hashes distintos y no se puede revertir.

Flujo de login

  1. Flutter: POST /auth/login con {"email","password"}, sin token.
  2. AuthService.login busca por correo y compara la contraseña con passwordEncoder.matches.
  3. Si coincide, TokenService genera los dos tokens y se responde {access_token, refresh_token, token_type, expires_in}.
  4. Flutter guarda los tokens y desde ahí manda Authorization: Bearer <access>.
  5. A los 60 minutos la API responde 401. Flutter llama solo a /auth/refresh, recibe tokens nuevos y repite la petición (ver sección 22).
CORSEl navegador bloquea las peticiones de una página (localhost:5xxx, Flutter Web) a otro origen (localhost:8081) salvo que el servidor lo permita. corsConfigurationSource() permite cualquier origen y los métodos GET, POST, PUT, PATCH, DELETE. En Android o escritorio no aplica: CORS es solo cosa de navegadores.
Detalle real del proyectoSi una petición a una ruta pública lleva un token inválido, Spring responde 401 igual. Por eso Flutter nunca manda token a login, register ni refresh (ApiConfig.publicAuth).

18. Una petición, clase por clase

Ejemplo: el admin cancela el pedido 7 → PATCH /api/v1/orders/7/status con {"status":"CANCELADO"}.

  1. Tomcat recibe la conexión en el 8081 y se la pasa a Spring.
  2. Filtros de Spring Security: CORS ok → el JwtDecoder valida el token → el converter crea la autenticación con ROLE_ADMIN → la regla PATCH /api/v1/orders/*/status → hasRole("ADMIN") se cumple.
  3. DispatcherServlet encuentra OrderController.updateStatus.
  4. Jackson convierte el JSON en StatusRequest; el texto "CANCELADO" se convierte en el enum OrderStatus.CANCELADO. @Valid revisa @NotNull.
  5. OrderService.updateStatus abre la transacción y busca el pedido (orders.findById). Si ya estaba cancelado lanza 400; si no, devuelve el stock de cada ítem y cambia el estado.
  6. Hibernate, al cerrar la transacción, detecta los cambios (dirty checking) y ejecuta los UPDATE de sneakers y orders.
  7. El service devuelve OrderResponse.from(order); Jackson lo pasa a JSON y se responde 200.
  8. Si algo lanzó ApiException, el GlobalExceptionHandler arma el JSON de error.

2. ApiClient: Dio con interceptor

Dio es el cliente HTTP. Se crea una sola instancia compartida con la URL base y tiempos de espera de 10 s. Lo importante es el interceptor: código que se ejecuta antes de cada petición y cuando llega un error.

lib/config/api/api_client.dart (resumido) 
class _AuthInterceptor extends QueuedInterceptor {
  // ANTES de cada petición: pegar el token (menos en login/register/refresh)
  onRequest(options, handler) async {
    if (!ApiConfig.publicAuth.contains(options.path)) {
      final token = await storage.read(key: StorageKeys.token);
      if (token != null) options.headers['Authorization'] = 'Bearer $token';
    }
    handler.next(options);
  }

  // SI LLEGA UN ERROR: si es 401, renovar el token y repetir la petición
  onError(err, handler) async {
    if (err.response?.statusCode != 401) return handler.next(err);
    final token = await _refresh();                 // POST /auth/refresh
    if (token == null) {                            // también venció el refresh
      await clearTokens(); ApiClient.onSessionExpired?.call(); // → login
      return handler.next(err);
    }
    err.requestOptions.headers['Authorization'] = 'Bearer $token';
    handler.resolve(await _plain.fetch(err.requestOptions)); // repetir
  }
}

Así ninguna pantalla tiene que preocuparse por el token: el usuario ni nota que venció. Es QueuedInterceptor para que, si fallan 3 peticiones a la vez, el refresh se haga una sola vez y las demás esperen en cola.

El estado es inmutable: no se hace state.add(x), se asigna una lista nueva. Riverpod compara la referencia, y si es otra, avisa a todos los que hacen watch (el badge del carrito, la pantalla del carrito, el detalle).

31. Preguntas que el profesor puede hacer

Ábrelas una por una e intenta responder antes de leer.

Spring y arquitectura

¿Qué es Spring Boot y qué diferencia tiene con Spring?
Spring es el framework (IoC, MVC, Data, Security…). Spring Boot lo hace fácil: starters, auto-configuración según lo que hay en el classpath, servidor Tomcat embebido y configuración en application.properties. La API se ejecuta como un programa normal con main.
¿Qué es la inversión de control y la inyección de dependencias?
IoC: el framework controla la creación y el ciclo de vida de los objetos, no tu código. DI: las dependencias se entregan desde afuera. En el proyecto, por constructor: OrderService recibe OrderRepository, UserRepository y SneakerService sin hacer new.
¿Qué es un bean? ¿Cómo se crea?
Un objeto administrado por el contenedor de Spring, singleton por defecto. Se crea anotando la clase (@Service, @RestController, @Component), con métodos @Bean en una clase @Configuration (como PasswordEncoder o JwtEncoder), o automáticamente para los repositorios.
¿El proyecto es MVC?
Usa Spring MVC con arquitectura en capas: Controller → Service → Repository → BD. El controller es la C; el modelo está en services, repositories y entidades; la “vista” es el JSON (DTOs), y la interfaz real la dibuja Flutter.
¿Por qué separar controller y service?
Responsabilidad única. El controller solo traduce HTTP ⇄ Java y valida la entrada; el service tiene las reglas (stock, permisos, transacciones) y no sabe nada de HTTP. Así las reglas se pueden reutilizar y probar sin servidor.
¿Diferencia entre @Controller y @RestController?
@RestController = @Controller + @ResponseBody: lo que devuelve el método se convierte en JSON en el cuerpo de la respuesta. @Controller solo se usa para devolver vistas HTML (por ejemplo con Thymeleaf).
¿Qué hace @SpringBootApplication?
Junta @Configuration, @EnableAutoConfiguration y @ComponentScan (busca beans en com.sneakhub.api y subpaquetes).
¿Qué es un DTO y por qué no devuelven las entidades?
Objeto solo para transportar datos. Evita exponer la contraseña, evita ciclos infinitos al pasar a JSON (Order ↔ OrderItem), permite cambiar la tabla sin romper el cliente y da una forma cómoda (subtotal, nombre del tenis). Son record.
¿Cómo se validan los datos que llegan?
Con Bean Validation en los DTOs (@NotBlank, @Email, @Positive, @NotEmpty, @Min…) y @Valid en el controller. Si falla, Spring no ejecuta el método y el GlobalExceptionHandler responde 400 con los errores por campo. Las reglas de negocio (stock, duplicados) se validan en el service.
¿Cómo se manejan los errores?
Los services lanzan ApiException con su código HTTP (notFound, conflict…). @RestControllerAdvice + @ExceptionHandler en GlobalExceptionHandler las atrapa todas y responde un JSON uniforme {status, message, errors, timestamp}.
¿Qué es @Transactional? ¿Qué pasa si falla a mitad?
Ejecuta el método en una transacción: todo o nada. Si se lanza una excepción (por ejemplo sin stock en el tercer ítem), se hace rollback y no queda nada guardado. readOnly = true en consultas optimiza.
¿Por qué el método update no llama a save()?
Por dirty checking: dentro de la transacción la entidad está administrada por Hibernate; al cambiar sus atributos, Hibernate genera el UPDATE automáticamente al hacer commit.

Base de datos y JPA

¿Qué base de datos usa y cómo se creó?
H2, embebida, en el archivo api/data/sneakhub.mv.db. H2 crea el archivo al conectarse por primera vez (URL jdbc:h2:file:./data/sneakhub), Spring Boot configura el DataSource, Hibernate crea las tablas desde las entidades con ddl-auto=update y el DataSeeder inserta los datos iniciales.
¿Qué diferencia hay entre JPA y Hibernate?
JPA es la especificación (interfaces y anotaciones como @Entity, @Id). Hibernate es la implementación que genera el SQL y lo ejecuta. Spring Data JPA va encima y genera los repositorios.
¿Cómo funciona findByUserEmailOrderByCreatedAtDesc si nadie lo implementó?
Spring Data analiza el nombre: findBy + propiedad user.email + OrderBy createdAt Desc, y genera la consulta con su JOIN al arrancar.
¿Qué relaciones hay entre las tablas?
Sneaker → Brand y Sneaker → Category (@ManyToOne); Order → User (@ManyToOne); Order → OrderItem (@OneToMany con cascade); OrderItem → Sneaker (@ManyToOne). Tallas e imágenes son @ElementCollection (tablas sneaker_sizes, sneaker_images).
¿Por qué OrderItem guarda unitPrice si el tenis ya tiene precio?
Para conservar el precio histórico. Si el admin cambia el precio, los pedidos anteriores deben mantener lo que el cliente pagó.
¿Por qué no se puede borrar un tenis con pedidos?
Los order_items tienen una llave foránea hacia él; borrarlo rompería el historial. El service lo verifica con existsBySneakerId y responde 409. La alternativa es poner el stock en 0.
¿Qué cambiarías para usar MySQL?
La dependencia (mysql-connector-j en vez de h2) y la URL, usuario y clave en application.properties, además de crear la base vacía en MySQL. El código Java no cambia.
Dos clientes compran el último par a la vez: ¿qué pasa?
Las dos transacciones podrían leer stock 1 y el stock quedaría en −1. Se soluciona con bloqueo optimista (@Version en Sneaker) o pesimista (@Lock en la consulta). Hoy el proyecto no lo implementa; es una buena mejora para mencionar.

Seguridad

¿Qué es un JWT y qué lleva el de SneakHub?
Un token firmado header.payload.firma. Lleva sub (correo), role, type (access o refresh), iss, iat y exp. Se firma con HS256 y la clave secreta; si se modifica, la firma no coincide.
¿Por qué es “stateless”?
El servidor no guarda sesiones: cada petición trae el token con toda la información necesaria y basta con verificar la firma. Escala mejor y no necesita cookies (por eso se desactiva CSRF).
¿Para qué el refresh token?
El access dura 60 minutos para que, si lo roban, sirva poco. El refresh (7 días) solo sirve para pedir tokens nuevos en /auth/refresh, así el usuario no tiene que volver a iniciar sesión. Un validador impide usar uno en lugar del otro.
¿Cómo se protege una ruta por rol?
En SecurityConfig: .requestMatchers(CATALOG).hasRole("ADMIN"). El converter lee el claim role y crea la autoridad ROLE_ADMIN. En los pedidos, el service además revisa que el cliente solo vea los suyos (403).
Diferencia entre 401 y 403
401: no autenticado (sin token, token inválido o vencido, credenciales malas). 403: autenticado pero sin permiso (cliente creando un tenis).
¿Cómo se guardan las contraseñas?
Con BCrypt (passwordEncoder.encode): hash lento con sal, no reversible. En el login se compara con matches.
¿Qué es CORS y por qué se configuró?
Es una regla del navegador que bloquea peticiones a otro origen salvo que el servidor lo permita. Flutter Web corre en otro puerto que la API, por eso corsConfigurationSource lo permite.

Flutter

¿Cómo consume la app la API?
Con Dio. ApiConfig tiene la URL base; ApiClient tiene una instancia de Dio con un interceptor que agrega el Bearer y renueva el token ante un 401; los services hacen get/post/put/patch/delete y convierten el JSON con fromJson.
¿Qué es un interceptor y qué hace el del proyecto?
Código que se ejecuta en cada petición o respuesta. El del proyecto pega el token (menos en login, register y refresh) y, si llega 401, llama a /auth/refresh, guarda los tokens nuevos y repite la petición; si no puede, limpia la sesión y manda al login.
¿StatelessWidget vs StatefulWidget?
Stateless no cambia por sí mismo; Stateful tiene estado interno y se redibuja con setState. El estado compartido entre pantallas se maneja con Riverpod.
¿Qué es un provider? ¿watch vs read?
Un contenedor de estado global de Riverpod. watch lee y se suscribe (el widget se redibuja si cambia), se usa en build. read lee una vez, se usa en eventos como onPressed. invalidate fuerza a recargar.
¿Cómo se actualiza el catálogo cuando cambias un filtro?
sneakersProvider hace ref.watch(sneakerFilterProvider). Al cambiar el filtro se recalcula, llama a la API con los query params nuevos y la pantalla (que observa el provider) se redibuja.
¿Qué son Future, async y await?
Un Future es un valor que llegará después (la respuesta HTTP). await espera sin congelar la interfaz y solo se puede usar dentro de funciones async.
¿Cómo protege la app las rutas?
El redirect de go_router lee el rol del JWT guardado: sin sesión manda al login; un cliente no entra a marcas, categorías ni al formulario; el admin no tiene carrito. La seguridad real igual está en la API.
¿Dónde se guarda el token? ¿Por qué no en shared_preferences?
En flutter_secure_storage, que cifra los datos. shared_preferences es texto plano y solo se usa para el tema y el idioma.
¿Por qué validar el stock en la app si la API ya lo valida?
Para dar respuesta inmediata al usuario sin esperar a la red. Pero la validación que vale es la del servidor: nunca se confía en el cliente.
¿Por qué el emulador usa 10.0.2.2?
En el emulador, localhost es el emulador mismo; 10.0.2.2 es la dirección especial que apunta al PC donde corre la API.
¿Cómo funciona el cambio de idioma?
Archivos .arb por idioma → flutter gen-l10n genera AppLocalizations. languageProvider guarda el Locale (persistido en shared_preferences) y MaterialApp lo usa.
