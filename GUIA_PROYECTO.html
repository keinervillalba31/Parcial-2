SneakHub: el proyecto explicado y Spring Boot desde cero

Una tienda de tenis con dos partes: una API REST en Spring Boot (carpeta api/) y una app en Flutter (carpeta lib/) que la consume. Esta guía da por hecho que sabes Java y explica cada pieza de Spring con el código real del proyecto.

1. Qué hay hecho hasta ahora

Backend y app completos: la app Flutter usa todos los endpoints de la API.

Listo API Spring Boot

Usuarios con roles, login con JWT, CRUD de tenis, marcas, categorías y pedidos con control de stock. Base de datos H2 en archivo.

Listo Flutter: sesión

Login, registro, renovación automática del token y rutas protegidas por rol.

Listo Flutter: ADMIN

Dashboard, CRUD de tenis, marcas, categorías y gestión del estado de los pedidos.

Listo Flutter: cliente

Catálogo con filtros, detalle, carrito, compra y "Mis pedidos".

2. Spring explicado desde Java

Primero una aclaración: se escribe Spring (primavera), no "Sprint". Spring Framework es la base y Spring Boot es una capa encima que lo configura casi todo por ti.

El problema que resuelve

En Java puro, para tener un servidor web que guarde en una base de datos tendrías que crear tú mismo el servidor HTTP, abrir conexiones JDBC, convertir JSON a objetos a mano, crear los objetos y pasarles sus dependencias en el orden correcto. Spring se encarga de todo eso. Tú escribes clases normales y les pones anotaciones (@Algo) que le dicen a Spring qué papel cumple cada una.

Idea central nº 1: Inversión de Control (IoC) y los "beans"

En Java normal tú haces new. En Spring, Spring crea los objetos por ti al arrancar y los guarda en un contenedor llamado ApplicationContext. Cada objeto que maneja Spring se llama bean. Por defecto hay una sola instancia de cada bean (un singleton) compartida por toda la app.

Java puro

var repo = new SneakerRepositoryImpl(conexion);
var catalog = new CatalogService(brandRepo, catRepo);
var service = new SneakerService(repo, itemsRepo, catalog);
var controller = new SneakerController(service);
// ...y además montar el servidor HTTP

Con Spring

@Service
public class SneakerService {
  public SneakerService(SneakerRepository sneakers,
                        OrderItemRepository orderItems,
                        CatalogService catalog) { ... }
}
// Spring ve el constructor, busca esos 3 beans
// y se los pasa. Tú nunca haces new.

Idea central nº 2: Inyección de Dependencias (DI)

Fíjate que en todo el proyecto los servicios y controllers reciben lo que necesitan por el constructor y lo guardan en campos final. Eso es inyección de dependencias por constructor, la forma recomendada. Spring mira los tipos de los parámetros y pasa el bean de ese tipo. Si una clase tiene un solo constructor, ni siquiera hace falta anotarlo con @Autowired.

Así es como Spring "arma el árbol" de objetos de esta API al arrancar:

¿Cómo sabe Spring qué clases son beans?

Al arrancar, Spring recorre el paquete com.sneakhub.api y todos sus subpaquetes (esto se llama component scan) buscando clases con estas anotaciones:

AnotaciónSignificaEn el proyecto
@Component"Esto es un bean", en generalDataSeeder
@ServiceUn bean con lógica de negocio (es un @Component con otro nombre)AuthService, SneakerService…
@RestControllerUn bean que atiende peticiones HTTP y responde JSONSneakerController…
@ConfigurationUna clase cuyos métodos @Bean fabrican beansSecurityConfig, JwtConfig
@BeanEn un método: "lo que devuelva este método, regístralo como bean"passwordEncoder(), jwtEncoder()

Los repositorios (interface ... extends JpaRepository) son un caso especial: Spring Data los detecta y genera la implementación por ti. Lo vemos en la sección 6.

¿Para qué sirve @Bean si ya existe @Component?Para registrar objetos de clases que no son tuyas y no puedes anotar. BCryptPasswordEncoder viene de una librería, así que en SecurityConfig hay un método @Bean que lo crea. Desde ese momento cualquier clase puede pedir un PasswordEncoder en su constructor, como hacen AuthService y DataSeeder.

Idea central nº 3: Autoconfiguración y "starters"

Spring Boot mira qué librerías tienes en el pom.xml y configura cosas automáticamente. Por ejemplo, si ve el driver de H2 y JPA, crea el pool de conexiones y Hibernate. Si ve spring-boot-starter-webmvc, levanta un Tomcat embebido, así que no despliegas ningún .war: la app es el servidor. Un starter es un paquete de dependencias que trae todo lo necesario para una función.

Idea central nº 4: configuración en application.properties

Las que empiezan por spring. o server. las lee Spring Boot. Las que empiezan por app. las inventamos nosotros y se leen en el código con @Value:

3. Arranque y pom.xml

SneakHubApiApplication.java

@SpringBootApplication
public class SneakHubApiApplication {
    public static void main(String[] args) {
        SpringApplication.run(SneakHubApiApplication.class, args);
    }
}

Es un main normal de Java. @SpringBootApplication junta tres anotaciones:

  • @Configuration: esta clase puede declarar beans.
  • @EnableAutoConfiguration: activa la autoconfiguración de la sección anterior.
  • @ComponentScan: busca beans en este paquete y sus subpaquetes. Por eso esta clase está en la raíz, com.sneakhub.api.

SpringApplication.run(...) crea el contenedor, instancia todos los beans, ejecuta los CommandLineRunner (el DataSeeder) y levanta Tomcat en el puerto 8081.

Ejemplo completo: POST /api/v1/orders

  1. Llega la petición con Authorization: Bearer eyJ... y un JSON con los items.
  2. El filtro de seguridad valida la firma y la expiración del JWT y crea un objeto Authentication con el correo y el rol. Si el token falla, responde 401 y el controller nunca se ejecuta.
  3. Jackson convierte el JSON en un OrderRequest (record) y @Valid revisa sus anotaciones. Si algo falla, responde 400.
  4. OrderController.create llama a orderService.create(auth.getName(), request).
  5. OrderService abre una transacción, busca el usuario y cada tenis, valida talla y stock, arma el pedido, descuenta el stock y guarda.
  6. Convierte la entidad Order en OrderResponse y Jackson lo devuelve como JSON con estado 201.

5. Entidades (JPA / Hibernate)

Una entidad es una clase Java normal que representa una tabla. Hibernate traduce entre objetos y filas, así que no escribes SQL para lo básico.

entity/User.java (resumido)

@Entity                    // esta clase es una tabla
@Table(name = "users")     // nombre de la tabla ("user" es palabra reservada en SQL)
public class User {
    @Id                                             // llave primaria
    @GeneratedValue(strategy = GenerationType.IDENTITY) // autoincremental
    private Long id;

    @Column(nullable = false, unique = true)          // NOT NULL + UNIQUE
    private String email;

    @Enumerated(EnumType.STRING)  // guarda "ADMIN" y no 0 (más legible y seguro)
    private Role role;

    protected User() {}           // JPA exige un constructor vacío
    public User(String name, ...) { ... }
}

Las relaciones

CódigoQué significa en la BD
Sneaker: @ManyToOne Brand brand
@JoinColumn(name="brand_id")		Muchos tenis tienen una marca: columna brand_id en sneakers (llave foránea).
Order: @ManyToOne User userCada pedido es de un usuario: columna user_id.
Order: @OneToMany(mappedBy="order", cascade=ALL, orphanRemoval=true) List<OrderItem> itemsUn pedido tiene muchas líneas. mappedBy indica que la llave foránea está en OrderItem.order. cascade=ALL: al guardar el pedido se guardan sus líneas. orphanRemoval: si quitas una línea de la lista, se borra.
Sneaker: @ElementCollection List<Integer> sizesUna lista de valores simples (no de entidades). Se guarda en una tabla aparte, sneaker_sizes(sneaker_id, size). Lo mismo para images.

Con ddl-auto=update, Hibernate crea al arrancar estas tablas: users, brands, categories, sneakers, sneaker_sizes, sneaker_images, orders, order_items.

Detalle de diseño: el precio se congela en el pedidoOrderItem guarda su propio unitPrice, que se copia del tenis en el constructor. Si mañana el admin sube el precio, los pedidos viejos conservan el precio al que se compró.
Detalle de diseño: el total lo calcula el pedidoOrder.addItem() enlaza la línea con el pedido y suma al total. Así el total nunca queda desincronizado con las líneas.

6. Repositorios (Spring Data JPA)

Esta es la parte que más sorprende viniendo de Java: escribes una interfaz sin implementación y funciona.

public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);
    boolean existsByEmail(String email);
}

JpaRepository<User, Long> (entidad, tipo del id) ya trae gratis save, findById, findAll, delete, count, saveAll y más. Al arrancar, Spring genera una clase que implementa la interfaz y la registra como bean.

Consultas derivadas del nombre del método

Spring lee el nombre del método y arma la consulta:

MétodoConsulta generada (aprox.)
findByEmail(email)where email = ?
existsByNameIgnoreCase(name)select count(*) > 0 ... where lower(name) = lower(?)
existsBySneakerId(id)Navega la relación: where sneaker.id = ?
findByUserEmailOrderByCreatedAtDesc(email)join user ... where user.email = ? order by created_at desc
findAllByOrderByCreatedAtDesc()Todos, ordenados del más nuevo al más viejo

Consulta escrita a mano con @Query

Para los filtros del catálogo se usa JPQL, que se parece a SQL pero trabaja con clases y atributos Java (Sneaker s, s.brand.id), no con tablas:

repository/SneakerRepository.java

@Query("""
        select s from Sneaker s
        where (:brandId is null or s.brand.id = :brandId)
          and (:categoryId is null or s.category.id = :categoryId)
          and (:gender is null or s.gender = :gender)
          and (:q is null or lower(s.name) like lower(concat('%', :q, '%')))
        order by s.id
        """)
List<Sneaker> search(@Param("brandId") Long brandId, ...);

El truco (:x is null or ...) hace que cada filtro sea opcional: si el parámetro llega null, esa condición siempre es verdadera.

7. DTOs y validación

DTO (Data Transfer Object) es la forma del JSON que entra o sale. Están separados de las entidades a propósito.

¿Por qué no devolver la entidad directamente?

  • Seguridad: User tiene el campo password. UserResponse no lo tiene, así que es imposible filtrarlo por error.
  • Forma del JSON: el cliente manda brandId (un número), pero la entidad tiene un objeto Brand completo.
  • Evitar bucles: Order → items → order → … haría que Jackson entrara en recursión infinita.

Records de Java

Los DTOs son record (Java 16+): clases inmutables donde el compilador genera constructor, getters (email() en vez de getEmail()), equals y toString. Jackson los convierte a y desde JSON sin configuración. Se agrupan en una clase contenedora (AuthDtos, OrderDtos…) para tener pocos archivos.

dto/AuthDtos.java

public record RegisterRequest(
        @NotBlank(message = "El nombre es obligatorio") String name,
        @NotBlank @Email(message = "Correo inválido")       String email,
        @NotBlank @Size(min = 4, message = "...")           String password,
        String avatar) {}                                     // opcional

public record AuthResponse(
        @JsonProperty("access_token") String accessToken,  // en JSON se llama access_token
        ...) {}

@JsonProperty cambia el nombre en el JSON. Se usa porque la app Flutter espera access_token (snake_case) y en Java la convención es camelCase.

Cómo se activa la validación

Las anotaciones no hacen nada por sí solas. Se ejecutan cuando el controller pone @Valid delante del parámetro:

public AuthResponse register(@Valid @RequestBody RegisterRequest request)

Si algo falla, Spring lanza MethodArgumentNotValidException antes de entrar al método, y nuestro manejador de errores la convierte en un 400 con el detalle por campo. En OrderRequest, List<@Valid OrderItemRequest> hace que también se valide cada item de la lista.

El patrón from()

Cada DTO de respuesta tiene un método estático que convierte la entidad: SneakerResponse.from(sneaker). Así la conversión vive en un solo lugar.

8. Servicios y transacciones

Aquí están las reglas del negocio. El controller no decide nada; el servicio sí.

@Transactional

Todo lo que pasa dentro de un método @Transactional es una sola transacción de base de datos: o se guarda todo, o nada. Si se lanza una excepción a mitad de camino (por ejemplo, "stock insuficiente" en el tercer item), se hace rollback y el stock de los dos primeros no queda descontado. readOnly = true en las consultas es una optimización e indica que ese método no modifica nada.

Lo más raro de JPA: los cambios se guardan sin llamar a save()Mira SneakerService.update: 
Sneaker sneaker = get(id);   // entidad cargada dentro de la transacción
apply(sneaker, request);     // solo llama setters
return SneakerResponse.from(sneaker);   // ¡no hay save!
Una entidad cargada dentro de una transacción queda "gestionada" (managed). Al terminar el método, Hibernate compara la entidad con cómo estaba al cargarla y genera los UPDATE que hagan falta. Esto se llama dirty checking. Por eso OrderService descuenta el stock con un simple setStock(...) y en updateStatus tampoco hay save.

Las reglas de negocio del proyecto

ServicioReglas
AuthServiceEl correo se normaliza (trim y minúsculas). La contraseña se compara con BCrypt. Registrarse siempre da rol CUSTOMER. Correo repetido → 409. Si no mandas avatar, se asigna uno.
SneakerServiceTallas sin repetir y ordenadas. La marca y la categoría deben existir (404 si no). No se puede borrar un tenis con pedidos (409): se sugiere poner el stock en 0.
OrderServiceLa talla debe estar en las disponibles. Primero suma las cantidades por tenis (si pides el mismo tenis en dos tallas, cuenta el total contra el stock). Descuenta el stock. Un cliente solo ve sus pedidos (403 si intenta ver otro). Cancelar devuelve el stock, y un pedido cancelado ya no cambia de estado.
CatalogServiceNombre de marca o categoría único sin importar mayúsculas. Listas ordenadas por nombre.
TokenServiceGenera y valida los JWT (sección 11).
¿Por qué el DTO se arma dentro del servicio?Con spring.jpa.open-in-view=false, la conexión con la BD se cierra al salir del servicio. Las colecciones como sizes o items se cargan "perezosamente" (lazy): solo cuando las usas. Si el controller intentara leerlas después, fallaría con LazyInitializationException. Por eso los servicios devuelven DTOs ya armados y no entidades.

Fíjate también en que los métodos get(id) de SneakerService y CatalogService no tienen modificador (son package-private): otros servicios del mismo paquete los reutilizan, como OrderService, que llama a sneakerService.get(...), pero los controllers no.

11. Seguridad y JWT

La parte más densa. Vamos por piezas.

¿Qué es un JWT?

Un texto en tres partes separadas por puntos: cabecera.datos.firma. Los datos (claims) están en Base64, así que cualquiera puede leerlos, pero solo quien tiene la clave secreta puede generar una firma válida. Si alguien cambia "role":"CUSTOMER" por "ADMIN", la firma deja de coincidir y el token se rechaza. Los claims de nuestros tokens son:

{ "iss": "sneakhub-api", "sub": "cliente@sneakhub.com", "iat": ..., "exp": ...,
  "role": "CUSTOMER", "type": "access" }

El servidor no guarda sesiones: cada petición trae su token y con eso basta (stateless).

Access token y refresh token

access_token · 60 min

Va en cada petición (Authorization: Bearer ...). Dura poco para que, si lo roban, sirva poco tiempo.

refresh_token · 7 días

Solo sirve en /auth/refresh para pedir tokens nuevos sin volver a escribir la contraseña.

El claim type evita que se usen al revés. En JwtConfig.decoderFor(key, tipo) se añade un validador que exige type == "access" para el decoder que usa Spring en cada petición, y TokenService usa otro decoder que exige "refresh".

JwtConfig: firmar y validar

@Bean SecretKey jwtSecretKey(@Value("${app.jwt.secret}") String secret)  // clave HMAC-SHA256
@Bean JwtEncoder jwtEncoder(SecretKey key)   // lo usa TokenService para firmar
@Bean JwtDecoder jwtDecoder(SecretKey key)   // Spring Security lo detecta y lo usa en cada petición

Aquí se ve la DI con @Bean: jwtEncoder pide un SecretKey como parámetro y Spring le pasa el bean creado justo arriba.

SecurityConfig: las reglas

Spring Security funciona como una cadena de filtros que se ejecuta antes de cualquier controller. Se configura con un bean SecurityFilterChain:

http
  .csrf(csrf -> csrf.disable())            // CSRF protege sesiones con cookies; aquí no hay
  .cors(Customizer.withDefaults())         // permite llamadas desde el navegador (Flutter Web)
  .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))  // sin sesiones
  .authorizeHttpRequests(auth -> auth
      .requestMatchers("/h2-console/**", "/error").permitAll()
      .requestMatchers(POST, "/api/v1/auth/login", ...register, ...refresh).permitAll()
      .requestMatchers(GET, CATALOG).permitAll()        // ver catálogo: cualquiera
      .requestMatchers(CATALOG).hasRole("ADMIN")          // modificarlo: solo admin
      .requestMatchers(PATCH, "/api/v1/orders/*/status").hasRole("ADMIN")
      .anyRequest().authenticated())                    // lo demás: con token
  .oauth2ResourceServer(oauth -> oauth.jwt(...));       // "los tokens son JWT"
El orden importaLas reglas se evalúan de arriba hacia abajo y gana la primera que coincide. Por eso GET CATALOG → permitAll va antes de CATALOG → hasRole("ADMIN"). Si las invirtieras, nadie sin token podría ver los tenis.

¿Cómo se conecta el rol del token con hasRole("ADMIN")? Spring Security trabaja con "authorities" del tipo ROLE_ADMIN. El método jwtAuthenticationConverter() le dice: "lee el claim role y antepón ROLE_". Así "role":"ADMIN" se convierte en ROLE_ADMIN, y hasRole("ADMIN") busca justamente eso.

Contraseñas con BCrypt

Nunca se guarda la contraseña real. passwordEncoder.encode("admin123") produce algo como $2a$10$N9qo8uLO..., un hash con "sal" aleatoria (el mismo texto da un hash distinto cada vez). Para el login se usa passwordEncoder.matches(textoPlano, hashGuardado).

Respuestas de seguridad

401: no hay token, o es inválido o está vencido (o las credenciales del login son incorrectas). 403: el token es válido pero tu rol no alcanza, por ejemplo un cliente intentando crear un tenis.

14. Cómo correr y probar

Levantar la API

cd api
.\mvnw.cmd spring-boot:run      # PowerShell (Windows)
./mvnw spring-boot:run          # Git Bash / Linux / Mac

Necesitas JDK 17 o superior. Queda en http://localhost:8081. La primera vez Maven descarga las dependencias, así que tarda un poco más.

Probar con curl

# 1. Catálogo público (sin token)
curl "http://localhost:8081/api/v1/sneakers?gender=UNISEX&q=nike"

# 2. Login
curl -X POST http://localhost:8081/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"cliente@sneakhub.com","password":"cliente123"}'

# 3. Usar el token
curl http://localhost:8081/api/v1/auth/profile -H "Authorization: Bearer <access_token>"

# 4. Comprar
curl -X POST http://localhost:8081/api/v1/orders \
  -H "Authorization: Bearer <access_token>" -H "Content-Type: application/json" \
  -d '{"items":[{"sneakerId":1,"size":40,"quantity":2}]}'

Pruebas útiles para ver las reglas en acción: crear un tenis con el token del cliente (403), comprar el tenis 16, que tiene stock 0 (400), pedir una talla que no existe (400), o hacer login con una contraseña incorrecta (401).

Ver la base de datos

Abre http://localhost:8081/h2-console, con JDBC URL jdbc:h2:file:./data/sneakhub, usuario sa y sin contraseña. Ahí puedes hacer SELECT * FROM SNEAKERS y ver cómo baja el stock después de comprar.

16. Lo que sigue

El proyecto está completo. Mejoras posibles si quieres ir más allá:

  • Editar y eliminar marcas y categorías: la API hoy solo permite crearlas.
  • Subir imágenes como archivo en lugar de pegar URLs.
  • Paginación en GET /sneakers si el catálogo crece mucho.
Para seguir aprendiendoUn buen ejercicio es agregar tú mismo un endpoint siguiendo el patrón: por ejemplo PUT /api/v1/brands/{id}. Necesitas un método en CatalogService con @Transactional (busca, aplica los setters y aprovecha el dirty checking) y un @PutMapping en CatalogController. La regla de seguridad ya lo cubre, porque CATALOG sin GET exige ADMIN.
